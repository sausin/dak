# Internationalisation (i18n) and translation

Dak ships in English only today. Everything below exists so that adding a language is a translation job, not a
code change: drop in `values-<lang>/` files, list the language once, and it appears in the app.

## What a new language needs

1. Translations of every translatable string in `android/app/src/main/res/values/*.xml` **and**
   `android/core-telephony/src/main/res/values/*.xml` (failure reasons, flash SMS, MMS notices), as
   `values-<qualifier>/` files with the same file names. Qualifier: `hi` → `values-hi`, `pt-BR` → `values-pt-rBR`,
   `zh-Hans` → `values-b+zh+Hans` (`scripts/check-i18n.py` has the mapping).
2. One line in `android/app/src/main/res/xml/locales_config.xml` (BCP 47 tag, e.g. `<locale android:name="hi"/>`)
   and the same line in `android/app/src/debug/res/xml/locales_config.xml`.
3. `python3 android/scripts/check-i18n.py` passes (CI runs it through `scripts/tests/test_check_i18n.py`).

A language listed in `locales_config.xml` must be **complete**: the checker fails on any missing string. Work in
progress can sit in `values-<lang>/` without the `locales_config.xml` line; it is then only a warning, and users never
see a half-translated app (Android would otherwise fall back to English string by string).

## How the app picks its language

`app.dak.i18n.AppLocales` (and `LanguageDialog`, Settings → Appearance → Language):

- **Android 13+**: the framework's per-app language. `LocaleManager.setApplicationLocales` stores it, recreates
  activities and offers the same choice in system Settings → Apps → Dak → Language, listing `locales_config.xml`
  (`android:localeConfig` in the manifest).
- **Android 8–12**: `MainActivity` is a `FragmentActivity` (androidx.biometric needs one), not an
  `AppCompatActivity`, so AppCompat's `setApplicationLocales` + `autoStoreLocales` would store the choice but never
  apply it, and pulling in AppCompat only for this is not worth it. Dak stores the tag itself
  (`dak_app_locale` preferences) and applies it like AppCompat does: `applyOverrideConfiguration` in each activity's
  `attachBaseContext` (survives the `uiMode` changes MainActivity handles itself) and the application's resources
  (`applyToApplication`, re-applied in `onConfigurationChanged`) for notifications. `Locale.setDefault` is left
  alone on purpose: the phone-number country fallback reads the default locale's country.
- A phone upgraded from 12 to 13+ hands the stored choice to the framework once (`migrateToFramework`).
- The picker lists "System default" plus `locales_config.xml`, each language named in itself ("हिन्दी") with the
  current-language name under it.

When the language changes while Dak runs (system or app language), notification channel and group names are
rewritten at once: `DakApplication.onConfigurationChanged` → `NotificationChannels.onLocaleMaybeChanged()` (on
Android 8–12, `AppLocales.set` calls it, since no configuration change reaches the application). A process start in
a new language is already covered by the stored locale tag in `ensureCreated()`. No manifest `LOCALE_CHANGED`
receiver is needed: a running process always gets the configuration change, and a dead one re-checks on start.

## Where user-visible text comes from

| Text | Source | Notes |
|---|---|---|
| Screens, notifications, toasts | `app/src/main/res/values/strings*.xml` | Always `stringResource` / `getString`. |
| Settings titles, summaries, options, group names | `strings_settings.xml` | See below. |
| Premium feature summaries | `strings_settings.xml` (`feature_<name>_summary`) | Named by `Feature.stringKey`. |
| Send / MMS failure reasons | `core-telephony/.../strings_failures.xml` | See below. |
| Phone-maker battery steps (onboarding) | `strings_battery.xml` | `OemGuidance.steps` are `R.string` ids. |
| Automation undo snackbar | `strings_forwarding.xml` (`undo_rule_*`) | `AutomationUndo.text()`. |
| Self-test SMS body | `strings.xml` (`selftest_sms_body`) | Only the random token is matched. |
| Default forward template | `strings_forwarding.xml` (`fw_default_template`) | See below. |
| Birthday wish presets | `automations` `WishTemplates` | Multilingual presets, not resources (users pick any). |

### Settings labels (settings-registry is pure Kotlin)

`:settings-registry` cannot see `R`, so every label is named by a **resource name derived from stable data**
(`SettingsStringKeys`): `setting_<key with _>_title`, `..._summary`, `..._opt_<value>`, `settings_group_<group>`;
option lists shared by several rows carry an explicit `labelKey` (`swipe_action_*`). The registry keeps the English
literals: they are the fallback, what JVM tests read, and a second search vocabulary.

The app maps names to ids at compile time in `SettingsStringIds` (no `getIdentifier`: it is slow and invisible to
resource shrinking) and renders through `SettingsLabels` / `ResourceSettingsLabels`. Three tests keep it honest:

- `SettingsStringResourcesTest` (settings-registry, runs without the Android SDK): every registry name exists in
  `strings_settings.xml` with exactly the registry's English text (the failure message prints the XML to paste);
- `SettingsTextTest` (app): every name is in `SettingsStringIds` and points at the resource of that name; the
  app-declared Appearance rows' English matches;
- `SettingsEnglishGoldenTest` (settings-registry): pins every English label and the search ranking for a set of
  queries (written before the move to resources; regenerate with `DAK_UPDATE_GOLDEN=1` only for deliberate changes).

Adding a setting: add the record, then its strings (the test output lists them) and its lines in
`SettingsStringIds`. **Search** matches the text in the app language *and* the English title, summary and keywords
(`SettingsSearch.search(text = …)`), so "OTP" or "backup" finds its row in any language; English-only ranking is
unchanged (pinned by the golden).

### Failure reasons

Reasons still travel as strings (`SendResult.Failed.reason`, `MmsDownloadState.Failed.reason`, the send-failure
store, a scheduled send's `failureReason` column), but are now codes: `dak-fail:<Failure>|args` (`FailureReasons`).
`FailureReasonText.resolve(context, raw)` turns a code into text in the app language; anything else (reasons stored
by older versions, exception messages, carrier-supplied `retrieveText`, the MMSC status text from `ResponseStatus`)
is shown unchanged. `Failure.english` / `FailureReason.english()` reproduce the old English exactly (logs, tests).
Adding one: an enum entry, a `dak_telephony_fail_<name>` string with the same English, a line in
`FailureReasonText.stringRes`; `FailureReasonsTest` checks all three.

### Forward template and loop guard

New auto-forward rules get `fw_default_template` in the app language (`ForwardingSpec.defaultTemplate` falls back
to English when a translation drops `{body}` or has no literal lead). Existing rules keep the template they were
saved with. `ForwardLoopGuard` treats a message as an earlier Dak forward when it starts with the rule's own lead,
the English default lead (`Fwd from`, for stored rules and English-speaking Dak users) or the default lead of any
shipped language (`registerDefaultTemplates`, called at start with the string in every `locales_config` language).

### Birthday wishes

A new user's default templates are the presets of the app language (`WishTemplates.defaultFor`: `hi` → Hindi,
`hi-Latn` → Hinglish, otherwise English). Stored settings, and every template a user saved, are never changed.
`{occasion}` without a label reads `wish_fallback_occasion`; labels are lower-cased with the app language's rules.

## Formatting rules

- **Machine text uses `Locale.ROOT`**: identifiers, hashes, logs, protocol values (`"%02x".format(Locale.ROOT, b)`).
  Kotlin's `lowercase()` / `uppercase()` (no argument) are already locale-invariant (`Locale.ROOT`), so they are
  correct for keys and comparisons; the Turkish-i problem only exists with the deprecated `toLowerCase()` or
  `String.format` / `"...".format(...)` without a locale. Only user-visible text uses the app language's locale.
- **The app language's locale** is `resources.configuration.locales[0]` (activity or composition context for UI;
  the application context follows it too, see above), not `Locale.getDefault()`.
- **Money** (`MoneyDisplay`): grouping is Dak's (lakh/crore for INR or viewers in India, thousands otherwise), but
  digits and separators come from the locale's `DecimalFormatSymbols`: `ar-EG` shows `١٬٢٣٤٫٥٠`, never ASCII digits
  between Arabic separators.
- **Dates and times** use CLDR skeletons (`DateFormat.getBestDateTimePattern`), including date + time together
  (`dMMMyHm`) so the locale picks the order and the joiner; never concatenate a date and a time.
- **Sorting names** uses `Collator` for the app language (`ConversationChannels.list`, contact suggestions).
- **Strings with several placeholders are positional** (`%1$s`, `%2$d`) so translators can reorder; the checker
  fails otherwise. Counts use `<plurals>`.

## Checks

- `python3 android/scripts/check-i18n.py` — locale config vs `values-*`, completeness of shipped languages,
  placeholder parity (`%1$s` and `{sender}`), positional placeholders, `translatable="false"` respected.
  `--comments` also lists English strings with placeholders but no translator comment (the backlog: ~180 today,
  mostly in `strings_screens.xml`, `strings_forwarding.xml`, `strings_instruments.xml`, `strings_folding.xml`).
- **Lint** (`android/app/build.gradle.kts`, `lint {}`): `HardcodedText`, `SetTextI18n`, `StringFormatInvalid` and
  `DefaultLocale` are errors; `MissingTranslation` is a warning while only English ships (a partial translation must
  not break the build; completeness is enforced by the checker for listed languages instead). CI does **not** run
  full lint yet (only AGP's automatic `lintVital` during release builds, which checks fatal issues only and is
  unaffected). Run it locally with `./gradlew :app:lintFreeDebug`; the report is in
  `app/build/reports/lint-results-freeDebug.html`. Before adding it to CI, fix or baseline the existing findings
  (`lint { baseline = file("lint-baseline.xml") }`, then `./gradlew :app:updateLintBaseline` and commit the file).
- **Pseudo-locales**: debug builds enable `isPseudoLocalesEnabled`; pick *English (XA)* (accented and ~30% longer:
  finds truncation and hardcoded text) or *Arabic (XB)* (mirrored right-to-left: finds layout problems) in
  Settings → Appearance → Language.

## Translation workflow (humans, not machine dumps)

Translations are done by people who use Dak in that language; no bulk machine translation is committed.

1. **Platform**: a translation management system such as Crowdin or Lokalise, connected to the repository. Source
   files: `android/app/src/main/res/values/strings*.xml` and `android/core-telephony/src/main/res/values/*.xml`;
   export path `values-%android_code%/%original_file_name%`. Strings marked `translatable="false"` are skipped by
   both tools. Translator comments (`<!-- %1$s = ... -->` above a string) are shown as context; add one whenever you
   add a placeholder.
2. **Glossary** (kept in the platform, seeded from this list): *Dak* (brand, never translated), *OTP* (keep the
   abbreviation people see in bank SMS), *UPI*, *SIM*, *MMS*/*SMS*, *Premium* (plan name), *recycle bin* / *bin*
   (Dak's own bin, not the phone's), *automation*, *rule*, *forward* (auto-forwarding), *heads-up* (the
   notification before a scheduled send), *passbook*, *app lock*, *Jev* (cloud classification, brand). Placeholders
   `{sender}`, `{body}`, `{time}`, `{amount}`, `{merchant}`, `{sim}`, `{firstName}`, `{name}`, `{age}`,
   `{occasion}` are never translated.
3. **Review**: a second native speaker reviews in the platform; then screenshots on a device (or pseudo-locale runs
   for length) for the main flows: onboarding, inbox, conversation, settings, notifications.
4. **Ship**: when a language is complete and reviewed, the platform opens a PR with `values-<lang>/`; add the
   `locales_config.xml` lines in the same PR. CI runs the checker; the release notes mention the new language.
5. **Keep up**: new English strings appear in the platform on merge; a shipped language that falls behind fails the
   checker, so either translate before release or temporarily drop its `locales_config.xml` line.

Wording that is legally reviewed (privacy policy, consent disclosures in `premium-api` `Disclosures`) needs a
reviewed translation of its own and a new disclosure version; it is out of scope for community translation.

## Not done yet

- `ResponseStatus.describe` (MMSC status texts from `:mms-pdu`) and carrier-supplied failure text stay as sent.
- `ScheduledEmergencyPolicy.CANCEL_REASON` and exception messages stored as failure reasons stay English.
- Translator comments for existing placeholder strings (`check-i18n.py --comments`).
- `:classify` / `:finance` locale fixes belong to their owners.
